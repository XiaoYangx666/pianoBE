# 钢琴还原度与 MIDI 播放精度实验报告

- 生成时间：2026-11-15T15:06:31.937Z
- 实验入口：`packages/web` 的 **音频实验室**（`/lab`）
- 离线渲染：`node tools/audio-lab-render.mjs`；本报告：`python tools/audio-lab-analyze.py`
- 试听文件：`build/audio-lab/*.ogg`（A/B 连播对 B 做整体响度匹配）；也可以直接打开 `build/audio-lab/index.html` 逐个播放。

## 实验设置

- **力度音源**：VCSL Steinway B 的 vl2 / vl3 / vl4 三层真实采样（CC0），30 个基础键，4s，44.1kHz。
- **现有音源**：FluidR3 GM 的 0.5s / 2s / 4s 三档采样（正式包使用的默认音色）。
- **力度处理**：多层模式下三层响度先对齐，再套同一条力度→响度曲线；因此差异只来自音头与泛音，不是音量。
- **调度**：所有方案使用同一批音符、同一力度、同一时值，只改变起始时间网格。
- **释放**：同一音源、同一力度，只改变 Note Off 后的释放包络。
- **A/B 试听**：连播时把 B 的整体响度匹配到 A（避免“谁更响谁更好听”）；单个方案文件保留原始电平，表格中的 LUFS 也来自原始文件。

## 曲目与片段

- **LiSA 红莲华（高密度快歌）**：片段 112.0–142.0s，564 音符，18.8 音符/秒（`midis\files\LiSA 红莲华.mid`）
- **周杰伦 枫（慢速表情）**：片段 126.0–156.0s，259 音符，8.6 音符/秒（`midis\files\周杰伦 - 枫.mid`）

## 实验页怎么用

1. 打开 `/lab`，选择内置音型、服务端曲目或本地 MIDI；设置片段起点/长度。
2. 点一个预设（力度 / 调度 / 释放 / 游戏现状 vs 改进），或直接编辑 A/B 两张方案卡。
3. 先点“匹配 A/B 响度”，再点“A → B 连播”；浅色竖线是原始 MIDI 位置，实色圆点是实际触发点。
4. 需要离线对比时点“导出 A/B”，导出与试听使用同一套采样与包络；指标不会因输出增益改变。

## 结论

### 1. 多力度真实采样相比单纯调音量，改善有多大？

- 在力度探针中，单层方案的频谱质心只变化 **-7 Hz**，三层方案变化 **+514 Hz**；弱/中/强层的平均质心分别为 **948 / 1241 / 1460 Hz**，说明不同力度层确实换了音头与泛音结构，而不是同一采样调音量。
- 三层方案的相邻力度 RMS 平均步进为 **0.75 dB**；层切换处（40→44 力度 RMS +1.31 dB（层贡献 -0.01 dB）；84→88 力度 RMS +0.38 dB（层贡献 -0.26 dB））与普通相邻力度的步进同量级，没有出现突兀的响度台阶。
- 结论：多力度采样带来的不是“更响”，而是弱奏更柔、强奏更亮、重音层次更清楚。片段中的三层使用量为：LiSA 弱/中/强 **0 / 195 / 369**，枫 **98 / 153 / 8**；快歌整体力度偏高，主要受益于 vl3/vl4 的音色差异；慢速曲的弱奏更多，vl2 的价值更明显。

### 2. 50ms 调度误差有多严重？哪种策略更合理？

- 当前“向上取整”在《红莲华》片段上平均拖后 **+24.9 ms**，P90 **44.8 ms**，相邻音间隔被改变超过 20ms 的比例 **23%**。
- “最近 tick”把平均误差降到 **+0.0 ms**，但 P90 仍有 **22.9 ms**；它减少的是整体拖后，不是网格本身。
- 对 120 BPM 十六分（125ms），50ms 网格仍会把间隔变成 100/150ms 交替；“提前 1 tick”只是把误差从偏后改成偏前，不能恢复原始间隔，听感上可能更激进。
- 结论：如果是 20 TPS 游戏端，**最近 tick 比向上取整更合理**（误差居中、不会整体拖后）；但它只能减轻、不能消除量化。真正接近原始节奏需要子 tick 调度，见可行性部分。

### 3. 当前三档采样和尾音处理是否显著影响还原度？

- 《红莲华》释放组：三档采样的尾音/时值比为 **5.09×**，最大声部 **22**；Note Off + 120ms 分别为 **2.23×** / **14**。
- LUFS：三档 **-15.3**，Note Off 120ms **-17.3**；三档把短音的 0.5s 尾音留在快速旋律里，容易和后续音符叠加；过长释放同样会浑浊。
- 结论：当前“<1s 全部走 0.5s 短档”对 88ms 中位时值的快歌不合适；短音尾音堆积明显。Note Off 控制能减少堆积，但释放不能太短，否则尾音被硬切、连奏不自然。建议在 80–150ms 之间按音区/力度细化，而不是统一一个值。

### 4. 哪些优化真正值得迁移到 Minecraft？

| 优化 | 听感收益 | 体积成本 | 运行开销 | 实现复杂度 | 建议 |
|---|---|---|---|---|---|
| 力度层（2–3 层） | 高：音头/泛音随力度变化 | 采样数 ×2–3 | 仅选层，几乎不变 | 中：打包、映射、层间校准 | **优先做 2 层**，先覆盖中音区 |
| 最近 tick | 中：消除整体拖后，误差居中 | 0 | 0 | 低 | **值得做**，但不能解决 100/150ms 交替 |
| Note Off 释放 | 中高：减少快歌尾音堆积 | 0（复用长采样） | 需保存/停止 SoundInstance | 中 | **值得做**，80–150ms 起 |
| 精确子 tick / 关键帧 | 高：真正恢复节奏 | 0 | 需要引擎支持 | 高 | 先做可行性原型，不建议本阶段实现 |
| 50ms 关闭量化 | 最高 | 0 | 0 | 不可行（20 TPS） | 游戏端做不到，浏览器实验仅作基准 |

### 5. 体积、开销与复杂度

- 本次实验的 VCSL 三层素材为 30 键 × 3 层 × 4s，OGG 共 **5.03 MB**；正式 `classic_grand` 的三档采样目前约 **1.95 MB / 90 个文件**，做成 2 层约 **3.9 MB / 180 个文件**，3 层约 **5.85 MB / 270 个文件**（按同等码率估算）。
- 运行时只多一次“按力度选层”的查表，CPU 开销可忽略；内存增加取决于同时解码的采样数。如果游戏端像 Web 播放器一样全量预解码，270 个文件的内存约为现在的 3 倍，需要改成按需加载或只对常用音区做多层。
- Note Off 需要保存每个音符的 `SoundInstance` 并在时值结束时 `stop()`，是本次改动中复杂度最高的一项；但它不需要新增采样，性价比高。
- 力度层建议先做 2 层（vl2/vl4 或按音区选层），并复用本次的“层间响度对齐 + 统一力度曲线”方法，避免切换层时出现响度台阶。

## Minecraft 端可行性分析（不实现）

### 20 TPS 的硬约束

- 服务端脚本每 tick 推进一次，`currentTime` 以 50ms 为步进；`processPlayback()` 只会在 tick 边界触发 `playSound`。因此任意 MIDI 的起始时间只能落在 50ms 网格上，这是当前误差的根源。
- 把触发策略从“向上取整”改成“最近 tick”是纯服务端改动，不需要新资源，也不增加运行开销；它能把平均误差从约 +25ms 拉到 0ms 附近，但 120 BPM 十六分的 100/150ms 交替仍然存在。

### 子 tick 方案一：客户端动画/音效关键帧

- 基岩版客户端动画控制器的 sound effects 关键帧可以按渲染帧触发，理论上能获得 16.7ms 级（60fps）甚至更细的时间分辨率。
- 代价：需要为每首曲子生成动画/关键帧数据并随资源包下发，播放状态、暂停、跳转、多人同步都要重新实现；这等于把播放器从“服务端事件流”改成“客户端时间轴”，复杂度远高于当前方案。
- 结论：技术上可行，但不适合作为本轮优化；除非以后要做“音乐会级”回放，否则不建议。

### 子 tick 方案二：预制静音偏移采样

- 在采样前面预置不同长度的静音（例如 0/12.5/25/37.5ms），提前一个 tick 触发，让声音在目标时刻到达。
- 代价：每个采样需要 2–4 个偏移版本，资源体积和缓存成倍增加；而且只能“延迟”，不能“提前”，对不同的 tick 相位需要动态选择版本，打包与映射都更复杂。
- 结论：可以把量化误差压到约 ±12.5ms，但资源成本高、收益不如先把力度层和 Note Off 做好；本阶段只做可行性记录，不实现。

### 推荐迁移顺序

1. **力度层（先 2 层）**：收益最大，不改变调度架构；需要重新打包采样与层间校准。
2. **Note Off 释放**：复用现有长采样，只需保存 `SoundInstance` 并在时值结束时 `stop()`；对快歌的尾音堆积改善明显。
3. **最近 tick**：改动最小，先把整体拖后消掉；不要期待它恢复 16 分音符的原始间隔。（已实现：`SCHEDULE_LEAD_TICKS`）
4. **子 tick**：等前三项稳定后再评估，不建议本阶段投入。

## 限制

- 离线渲染使用线性重采样与简化包络，和 WebAudio/Minecraft 的实际输出不会逐样本一致；结论以相对差异和听感为准。
- 快速曲目片段只取 30s；不同段落的密度/力度分布会变化，建议在实验页换片段重复试听。
- 力度层响度对齐使用了 1.2s 积分响度；极短音符的实际感知响度可能略有不同。
- 游戏端仍受 20 TPS 限制；除“最近 tick”（提前半个游戏 tick 触发）外，本阶段没有修改游戏播放逻辑，也没有重新打包正式音色资源。
